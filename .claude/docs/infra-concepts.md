## 1. 지연의 계단 — 모든 선택지의 실제 차이

```
같은 프로세스 함수 호출     나노초~마이크로초    직렬화 없음
루프백 HTTP (localhost)     수십 µs ~ 1ms 미만   직렬화 있음
같은 리전 서버 간 HTTP      수 ms ~ 수십 ms
사용자 회선 왕복            수십 ~ 수백 ms       모바일이면 더 큼
```

논의된 선택지들이 이 계단에서 어디에 앉는지가 판단의 핵심이었다.

-   **모놀리식 Next + DB 직접 접근** → 1번 칸 (직렬화조차 없음)
-   **EC2 코로케이션** (`Next → localhost:3001 → Express`) → 2번 칸
-   **Next → API Gateway → Lambda** → 3번 칸 + 콜드스타트
-   **브라우저 → apps/api 직접** → 4번 칸

## 2. RSC의 "렌더 중 DB 접근"이 실제로 뜻하는 것

```tsx
export default async function TodayPage() {
    const question = await db.question.findFirst(...); // ← 여기서 렌더가 멈춤
    return <QuestionCard question={question} />;
}
```

**"렌더 중"은 "공짜로 곁에서 처리된다"는 뜻이 아니다.** 서버 렌더 패스가 그 `await` 지점에서 멈춰 기다리고, DB 시간은 **서버 응답 시간에 그대로 포함**된다.

정확히는: 서버 렌더링은 async 함수다. React가 이 컴포넌트를 호출하면 Promise가 돌아오고, React는 그게 resolve될 때까지 출력 생성을 보류한다. 그동안 **형제 컴포넌트는 계속 렌더되고 그 안의 다른 `await`도 동시에 출발**한다. 이것이 "렌더 중"의 실제 의미.

### 이득의 정체 — 시간이 줄지 않고, 붙는 위치가 바뀐다

```
클라이언트 fetch:  [HTML 응답] → [JS 다운로드/파싱] → [hydrate] → [fetch → API → DB]
                   └─── 이 전부가 끝난 뒤에야 데이터 요청 출발 ───┘

서버 렌더:         [HTML 응답 ← 그 안에 API → DB 대기 포함]
                   └── TTFB가 그만큼 늘고, 대신 뒤에 붙는 게 없음 ──┘
```

**TTFB를 희생해 클라이언트 워터폴을 없애는 거래.** 총합이 보통 유리한 이유는 없어진 쪽(JS 로드 + 클라이언트 RTT)이 더 크기 때문.

### 두 가지 주의

-   **Suspense로 기다리는 위치를 쪼갤 수 있다.** 셸 HTML을 먼저 흘려보내고 DB 조회가 끝난 조각을 나중에 스트리밍 → TTFB 손해도 줄어든다.
-   **서버 쪽에도 워터폴이 생긴다.** 부모가 `await`한 결과를 자식이 받아 또 `await`하면 순차 실행. `Promise.all`로 펼쳐야 한다.

```tsx
// 나쁨: 순차
const question = await getQuestion();
const streak = await getStreak();
// 좋음: 병렬
const [question, streak] = await Promise.all([getQuestion(), getStreak()]);
```

`prefetchQuery`도 동일하다 — 서버 컴포넌트에서 `await`하는 순간 HTML 응답 시간에 포함되고, 여러 개는 `Promise.all`로 묶어야 한다.

## 3. Lambda 콜드스타트

**무엇**: Lambda는 요청이 없으면 실행 환경을 없애 둔다. 요청이 오면 컨테이너 생성 → Node 런타임 부팅 → 코드 다운로드/압축 해제 → 모듈 `import` 실행 → 그다음 핸들러 실행. 이 앞부분이 콜드스타트. 한 번 뜬 컨테이너는 잠시 재사용되고(관찰상 대략 5~15분 유휴 후 회수, **AWS가 보장하는 값 아님**) 그동안은 "웜".

**대략적 크기** (공개 벤치마크 기준 통상 범위, **이 앱의 측정값 아님**):

| 상황                               | 콜드         | 웜                |
| ---------------------------------- | ------------ | ----------------- |
| Node + 작은 번들                   | 100~400ms    | 한 자릿수~수십 ms |
| Express + AWS SDK v3 + `pdf-parse` | 500ms~1.5s   | 동일              |
| Next 서버를 Lambda에 (OpenNext)    | 1s 이상 흔함 | 동일              |

**이 앱에서 특히 문제인 이유**: 사용자 1명이 하루 한 번 → **거의 모든 요청이 콜드**. 평균 지연이 아니라 "매번 그 값을 낸다"고 봐야 한다. OpenNext는 서버 함수·이미지 최적화 함수가 나뉘어 있어 **콜드스타트가 겹칠 수도** 있다.

**완화책과 대가**

| 방법                                                                       | 효과          | 대가                                                             |
| -------------------------------------------------------------------------- | ------------- | ---------------------------------------------------------------- |
| 번들 축소 (AWS SDK v3에서 쓰는 클라이언트만 import, `pdf-parse` 지연 로딩) | 실질적        | 없음 — 무조건 할 가치 있음                                       |
| Provisioned Concurrency                                                    | 사실상 제거   | **시간당 과금** → 프리티어 전제 붕괴                             |
| EventBridge 워밍 핑 (5분마다)                                              | 부분적        | 호출 수는 프리티어 내지만 컨테이너 하나만 데워지고 널리 안티패턴 |
| EC2 (상시 프로세스)                                                        | **완전 제거** | 상시 과금 + 서버 운영                                            |

> Lambda SnapStart는 스냅샷으로 이를 줄이는 기능인데, Node 지원 여부는 확인 필요.

## 4. IaC (Infrastructure as Code)

**콘솔 클릭 대신 인프라를 코드/설정 파일로 선언하고, 그 파일을 실행해 생성·변경·삭제하는 것.**

```
콘솔:  브라우저에서 Lambda 생성 → 역할 붙이기 → API Gateway 만들기 → 연결 → ...
IaC:   infra/stack.ts 에 선언 → deploy 한 번 → 위 전부 자동 생성
       지우려면 remove 한 번 → 만든 것 전부 정리
```

**왜 중요한가**

-   **재현 가능성** — 콘솔로 만든 건 "어떻게 만들었는지"가 어디에도 없다. 3개월 뒤 본인도 모른다. IaC는 그 자체가 기록이고 git에 들어간다
-   **안전한 실습** — 만들고 지우기가 한 줄. **콜드스타트 실측 같은 실험이 부담 없어진다** (→ API Gateway 학습 트랙의 전제)
-   **비용 통제** — 실습 리소스를 지웠는지 확실히 알 수 있다. 콘솔로 만들다 보면 잊고 켜둔 리소스가 청구서에 나온다

**도구**

|                | 설명                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| CloudFormation | AWS 원조. YAML/JSON. 저수준, 장황                                          |
| **AWS CDK**    | TypeScript 등으로 작성 → CloudFormation 생성. 이 프로젝트가 TS라 궁합 좋음 |
| Terraform      | 멀티 클라우드 표준. 독자 언어(HCL)                                         |
| **SST**        | 아래 6절                                                                   |

PRD가 `infra/`에 "AWS CDK 또는 SST"라 적어둔 게 이 선택지다.

**순서 조언**: 개념 파악이 목적이면 **콘솔로 한 번 손으로 만들고 → IaC로 옮긴다.** IaC로 바로 시작하면 추상화가 개념을 감춘다.

## 5. API Gateway — HTTP API vs REST API

**API Gateway라는 서비스 안에 제품이 두 개**(WebSocket까지 세 개) 있다는 뜻.

-   **REST API** (2015년경) — 원조. 기능이 아주 많다: 요청/응답 변환(mapping template), API 키 + 사용량 플랜(쿼터/쓰로틀), 응답 캐싱, 요청 스키마 검증, WAF 연동, private 엔드포인트
-   **HTTP API** (2019년) — **대부분의 사용자는 그 기능들을 안 쓰고 그냥 Lambda로 요청을 통째로 넘기기만 한다**는 현실을 반영해 기능을 덜어내고 더 싸고 빠르게 만든 것 (통상 REST API의 1/3 가격대로 알려져 있으나 **정확한 요금은 확인 필요**)

**왜 둘 다 남아 있나**: AWS는 기존 API를 폐기하지 않는다. REST API 위에 돌아가는 프로덕션이 무수히 많아 없앨 수 없다. 그래서 실무 기준은 **"신규는 HTTP API, REST API에만 있는 특수 기능이 필요할 때만 REST API"**.

**이 앱**: Express를 통째로 프록시하는 게 전부(mapping template·API 키 플랜·캐싱 모두 미사용) → **HTTP API로 충분**.

**이름 함정**: 여기서 "REST API"는 아키텍처 스타일 REST가 아니라 **AWS 제품명**이다. HTTP API로도 REST 스타일 API를 만든다.

## 6. SST / OpenNext

둘은 같은 층이 아니다.

-   **OpenNext** — Next.js를 **Vercel 밖에 배포할 수 있게 빌드 결과를 변환해주는 오픈소스 어댑터.** Next 빌드 출력을 Lambda 핸들러 + 정적 자산 + 캐시 계층으로 재포장하고, Vercel이 자기 인프라로 제공하던 기능(middleware, 이미지 최적화, ISR, RSC 스트리밍)을 AWS 리소스에 매핑한다. 배포 도구가 아니라 **변환기**
-   **SST** — AWS 인프라를 TypeScript로 정의하는 **IaC 프레임워크**(=CDK/Terraform과 같은 층). Next·Remix·Astro 배포를 컴포넌트 한 줄로 제공하고, **Next 배포 시 내부적으로 OpenNext를 쓴다**

```
SST (IaC)  ──내부 사용──▶  OpenNext (Next → AWS 변환)  ──▶  Lambda + CloudFront + S3
```

OpenNext만 단독으로 CDK/Terraform과 조합하는 것도 가능.

**버전 주의**: SST v2는 CDK 기반, **SST v3("ion")은 Pulumi/Terraform 기반으로 완전히 재작성**됐다. 문서·예제가 버전에 따라 전혀 다르니 버전을 먼저 확인해야 한다. Next 14.2 호환 버전도 착수 전 확인 필요.

**대가**: 편하지만 **API Gateway·Lambda·CloudFront가 추상화 뒤로 사라진다** — 배포는 되는데 개념이 안 남는다.

## 7. 루프백 인터페이스

**커널이 제공하는 가상 네트워크 인터페이스.** 물리 하드웨어가 없고 소프트웨어로만 존재하는 네트워크 카드.

-   이름: Linux `lo`, macOS `lo0` / 주소: `127.0.0.1`, `::1` / `localhost`는 이 주소로 해석되는 호스트명
-   확인: `ifconfig lo0` (mac), `ip addr show lo` (Linux)

**동작**: 프로세스가 `127.0.0.1:3001`로 패킷을 보내면 커널 TCP/IP 스택이 "이 목적지는 나 자신"임을 인식하고, 물리 NIC로 내보내지 않고 **메모리 안에서 곧바로 수신 큐로 되돌린다**(loop back).

```
일반:   프로세스 → TCP/IP 스택 → NIC → 랜선/무선 → 라우터 → ... → 상대 머신
루프백: 프로세스 → TCP/IP 스택 → ┐
        프로세스 ← TCP/IP 스택 ← ┘   (메모리 안에서 끝)
```

**사라지는 비용**: 전파 지연 0, 패킷 손실·재전송 사실상 없음, MTU 매우 큼(보통 65536), 대역폭 상한이 메모리 복사 속도.
**남는 비용**: TCP/IP 스택 처리 + 메모리 복사 + 컨텍스트 스위치 → 수십 µs ~ 1ms 미만.

**부수적 보안 이점**: Express를 `0.0.0.0:3001`이 아니라 **`127.0.0.1:3001`에 바인딩**하면 루프백에만 붙으므로 **외부에서 접근할 방법이 원천적으로 없다.** 방화벽 규칙으로 막는 것보다 확실하다.

> 이건 이미 매일 쓰고 있는 것 — `pnpm dev`로 `localhost:3000`(Next), `localhost:3001`(Express)을 띄우는 게 전부 루프백. **코로케이션은 그 구성을 프로덕션에서도 쓰는 것.**

## 8. 소켓과 TCP는 왜 필요한가 (루프백인데도)

이유가 두 층. 하나는 피할 수 없고 하나는 선택의 결과다.

### 층 1 — 프로세스 격리 (피할 수 없음)

Next(프로세스 A)와 Express(프로세스 B)는 **별개의 OS 프로세스**다. OS가 프로세스 메모리를 격리하므로 A는 B의 변수에 손댈 수 없다. 데이터를 주고받으려면 **커널을 경유하는 IPC**가 반드시 필요하고, 소켓이 그 수단 중 하나다.

**소켓이란**: 커널이 관리하는 통신 종점(endpoint)의 핸들. 프로세스는 파일 디스크립터로 잡고 파일처럼 읽고 쓴다.

```
socket()   커널에 통신 종점 요청 → fd 받음
connect()  그 종점을 상대 종점에 연결
write()    데이터를 커널 버퍼에 씀
read()     커널 버퍼에서 읽음
close()    정리
```

이 층은 **프로세스를 합치지 않는 한 없앨 수 없다.** "모놀리식 Next + DB 직접 접근"이 빠른 이유가 정확히 이것 — 같은 프로세스라 이 층이 아예 없다.

### 층 2 — HTTP를 선택했기 때문 (선택의 결과)

Express는 HTTP 서버이고 **HTTP는 TCP 위에서 동작하도록 정의된 프로토콜**이다. "HTTP로 부른다"를 택한 순간 TCP 연결이 규약상 필수가 된다. 목적지가 같은 머신인지는 무관.

**TCP 연결이 하는 일**: 데이터 전송 전 3-way handshake(SYN → SYN-ACK → ACK)로 시퀀스 번호를 합의하고, 순서 보장·재전송·흐름 제어 상태를 만든다. 루프백에선 손실이 없어 그 보장이 사실상 불필요하지만 **TCP는 매체를 구분하지 않으니 절차를 그대로 밟는다.**

**keep-alive**는 그 낭비를 줄이는 것 — HTTP/1.1은 응답 후에도 연결을 열어두고 재사용하므로 핸드셰이크를 첫 요청에서 한 번만 낸다.

> Node에서 자동은 아니다. 내장 `fetch`(undici)는 커넥션 풀을 유지하지만 구식 `http.globalAgent`는 한동안 `keepAlive: false`가 기본이었다(Node 19쯤 true로 변경된 것으로 기억하나 **정확한 버전은 확인 필요**). `apiClient.ts`는 `fetch`를 쓰므로 현재는 문제없을 것.

## 9. Unix domain socket (UDS)

**UDS도 소켓을 쓴다.** `socket()`/`connect()`/`read()`/`write()` API가 그대로고, 다른 건 주소 패밀리(`AF_UNIX` vs `AF_INET`)뿐. 건너뛰는 건 소켓이 아니라 **TCP/IP 프로토콜 스택**이다.

**왜 건너뛸 수 있나**: UDS는 애초에 **같은 머신 안의 통신만을 목표로 설계**되어, 네트워크가 풀어야 하는 문제가 존재하지 않는다.

| TCP/IP가 하는 일   | 왜 필요한가                  | UDS에서는                                                       |
| ------------------ | ---------------------------- | --------------------------------------------------------------- |
| IP 주소 + 라우팅   | 수많은 머신 중 어디로 보낼지 | 목적지가 항상 자기 자신 → **파일시스템 경로** (`/run/api.sock`) |
| 포트 번호          | 한 머신의 여러 프로세스 구분 | 경로가 그 역할                                                  |
| 체크섬             | 전송 중 비트가 깨질 수 있음  | 메모리 복사라 깨지지 않음                                       |
| 시퀀스 번호·재전송 | 순서 변경·유실 가능          | 커널이 순서대로 버퍼에 넣음, 유실 없음                          |
| 3-way handshake    | 양쪽 상태 합의 필요          | 커널이 양쪽을 이미 알고 있음 → `connect()` 즉시 성립            |
| 흐름·혼잡 제어     | 대역폭 경쟁                  | 경쟁할 네트워크가 없음                                          |
| MTU 분할           | 물리 프레임 크기 제한        | 물리 매체가 없음                                                |

한 줄로: **TCP/IP 기능 대부분은 "믿을 수 없는 매체 위에서 신뢰성을 만드는 것"인데, 커널 메모리는 이미 신뢰할 수 있다.** 그래서 그 기계 장치가 통째로 불필요해지고 UDS는 커널 버퍼에 쓰고 읽는 것에 가까워진다. 프로토콜 헤더도 안 붙는다.

**부가 이점**: 파일시스템 권한(`chmod`/`chown`)으로 접근 제어. 포트를 안 쓰니 포트 충돌 없음.

### 이 앱에서는 TCP 루프백을 쓴다

**UDS는 같은 머신 전용**이라 나중에 Express를 별도 컨테이너로 분리하면 못 쓴다. ECS/EKS 방향을 보고 있으므로 `localhost:3001` → `api:3001`로 호스트명만 바꾸면 되는 **TCP가 이식성 면에서 낫다.** 성능 차이는 이 앱 규모에서 측정도 안 될 수준이므로 개념만 알고 넘어간다.
