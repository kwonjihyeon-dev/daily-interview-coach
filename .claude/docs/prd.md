## 1. 배경

매일 면접 준비를 습관화하려고 시작한 요청. 이메일/Slack 알림만으로는 습관 트리거 효과가 약하다는 판단 하에, 별도의 웹 서비스를 만들어 이력서/Notion 내용을 기반으로 맞춤 질문을 생성하고, 답변을 기록하며, 스트릭(연속 일수)으로 동기부여하는 방향으로 확정.

기존에 만든 Claude Artifact 프로토타입(로컬 스트릭 + 랜덤 질문 40개)은 컨셉 검증용이었고, 이번 PRD는 새 모노레포 + AWS 인프라로 정식 구현하기 위한 문서.

## 3. 아키텍처 결정 사항

### 3.1 AI 연동 — Anthropic API 직접 연동 vs AWS Bedrock

| 항목 | Anthropic API 직접 | AWS Bedrock |
| --- | --- | --- |
| 설정 난이도 | API 키 발급 즉시 사용 가능 | 콘솔에서 리전별 모델 액세스 신청 필요 (승인 대기 발생 가능) |
| 인증 방식 | Bearer 토큰(API 키) | AWS SigV4 (IAM 자격증명) |
| 최신 모델 반영 | 신모델 출시 즉시 사용 | 리전별로 반영이 늦는 경우 있음 |
| 과금 | Anthropic 계정 별도 청구 | 기존 AWS 청구서에 통합 |
| 네트워크 | 퍼블릭 인터넷 호출 | VPC 내부에서 PrivateLink로 호출 가능 |
| 적합한 상황 | 개인/소규모 프로젝트, 빠른 시작 | 이미 AWS 중심 인프라, VPC 격리·컴플라이언스 요구가 있는 조직 |

**결정: AWS Bedrock.** (변경 — 최초에는 설정 단순성을 이유로 Anthropic API 직접 연동을 택했으나, 어차피 Lambda + API Gateway로 AWS에 의존하는 구조라 재검토함) Bedrock을 쓰면 ① AWS 청구서 하나로 통합 ② Lambda 실행 역할(IAM Role)에 `bedrock:InvokeModel` 권한만 부여하면 되어 `ANTHROPIC_API_KEY`를 따로 저장/로테이션할 필요가 없음(보안·운영 이점) ③ Bedrock 모델 액세스 신청·IAM 설정 자체가 학습 목표에도 부합. 코드 변경은 크지 않음 — Anthropic SDK의 `Anthropic` 클라이언트 대신 `@anthropic-ai/bedrock-sdk`의 `AnthropicBedrockMantle` 클라이언트를 쓰고, 모델 ID에 `anthropic.` 접두사를 붙이면 나머지 호출 방식(메시지 생성 등)은 동일함. 유의점은 리전별 모델 액세스 신청이 필요하다는 것(Anthropic 모델은 계정당 최초 1회 use case 폼 제출 후 즉시 승인).

#### 3.1.1 모델 선택 및 가격 비교 (Bedrock, 2026-08 기준)

Bedrock에는 Anthropic 외에도 Amazon Nova, Meta Llama 등 더 저렴한 모델이 있으나, 이 프로젝트 규모(개인 1인, 하루 몇 회 호출)에서는 어느 모델을 써도 연간 비용 차이가 크지 않아 **가격보다 피드백 품질을 기준으로 결정**.

**Anthropic 모델 가격 (1M 토큰당, Bedrock 콘솔 확인)**

| 모델 | 입력 | 출력 |
| --- | --- | --- |
| Claude Haiku 4.5 | $1.00 | $5.00 |
| Claude Sonnet 5 | $2.00 | $10.00 |
| **Claude Sonnet 4 / 4.5 / 4.6** | **$3.00** | **$15.00** |
| Claude Opus 4.5 / 4.6 / 4.7 / 4.8 | $5.00 | $25.00 |
| Claude Fable 5 | $10.00 | $50.00 |

**용도별 예상 사용량과 비용** (AI 피드백: 입력 1K/출력 0.8K 토큰, 질문 생성: 월 1회 입력 3K/출력 2K 토큰, Sonnet 4.6 기준)

| 피드백 빈도 | 콜당 비용 | 연간 비용 |
| --- | --- | --- |
| 하루 1회 | $0.015 | 약 $5.48 |
| 하루 3회 | $0.015 | 약 $16.43 |

질문 생성(월 1회)은 별도로 연 $1 미만 — 두 작업 모두에 무의미한 수준의 비용 차이.

**결정: 두 작업(AI 피드백, 질문 생성) 모두 Claude Sonnet 4.6으로 통일. (Sonnet 5는 리전 문제로 안 됨)**

- 원래는 Sonnet 5(이전 세대보다 저렴하면서 더 최신)를 선택했으나, 실제 호출 시 계정 무관하게 `AccessDeniedException` 발생 — ap-northeast-2(서울), us-east-1(버지니아 북부) 모두 동일하게 막힘. root 계정, 결제 수단 등록 상태에서도 재현되고 같은 계정에서 Sonnet 4.6은 정상 호출되어, 계정/결제 문제가 아니라 **Sonnet 5 자체의 가용 리전/계정 롤아웃이 아직 제한적인 것**으로 판단
- Sonnet 5 액세스가 열리면 모델 ID만 바꿔서 전환 예정 ([`progress.md`](./progress.md) 참고)
- **모델 ID 확정** (AWS 공식 모델 카드 확인, 2026-08-06): Claude Sonnet 4.6은 ap-northeast-2(서울)에서 In-Region/Geo 둘 다 미지원, **Global Cross-Region Inference만 지원**. 따라서 bare 모델 ID(`anthropic.claude-sonnet-4-6`)가 아니라 `global.anthropic.claude-sonnet-4-6`을 `BEDROCK_MODEL_ID`로 사용해야 함 (`apps/api/.env.example`에 반영됨). 이전에 Opus 5/Sonnet 5 호출이 리전 무관하게 막혔던 것도 같은 이유(bare ID로는 최신 모델 대부분이 안 됨)일 가능성이 높음
- Opus는 이 용도(구조화된 정성 피드백 생성)에 비해 비용 대비 이득이 없어 제외
- Fable은 창작/롤플레이 특화 모델이라 인터뷰 피드백 도메인에 맞지 않아 제외
- 질문 생성처럼 실시간성이 필요 없는 작업은 Bedrock Batch 추론(최대 50% 할인)으로 추가 절감 가능하나, 원가 자체가 연 $1 미만이라 최적화 우선순위 낮음 — 모델 하나로 통일해 관리를 단순화하는 쪽을 선택

### 3.2 AWS 배포 방식 — Lambda+API Gateway vs ECS/Fargate vs EC2

| 항목 | Lambda + API Gateway | ECS/Fargate | EC2 |
| --- | --- | --- | --- |
| 운영 부담 | 거의 없음 (서버리스) | 중간 (오케스트레이션 필요) | 높음 (OS 패치·스케일링 직접 관리) |
| 비용 (저트래픽 기준) | 매우 저렴, 유휴 시 $0에 가까움 | 태스크가 항상 떠 있어 고정비 발생 | 인스턴스 24시간 과금 |
| 콜드스타트 | 있음 (드문 요청 시 지연 가능) | 없음 | 없음 |
| 확장성 | 자동, 사실상 무제한 | 오토스케일링 설정 필요 | 수동 또는 ASG 설정 필요 |
| 적합한 상황 | 개인 프로젝트, 트래픽 적고 불규칙 | 트래픽 예측 가능, 컨테이너 이미 익숙 | 세밀한 서버 제어가 꼭 필요한 경우 |

**결정: Lambda + API Gateway.** 사용자가 본인 1명이라 트래픽이 하루 몇 번 수준 — 서버리스가 비용/운영 부담 모두에서 압도적으로 유리함. Express 앱은 `serverless-http` 같은 어댑터로 감싸면 그대로 Lambda 핸들러로 배포 가능. **리전: `ap-northeast-2` (서울)** — 계정 확인 완료.

### 3.3 모노레포 구성 — Next.js 풀스택 vs Next.js+Node/Express 분리

| 항목 | Next.js 풀스택 (API Route) | Next.js + Node/Express 분리 |
| --- | --- | --- |
| 구조 복잡도 | 낮음 (앱 1개) | 높음 (앱 2개 + 공통 패키지 관리) |
| 배포 단위 | 프론트/백 항상 같이 배포 | 독립 배포 가능 |
| Lambda 배포 적합성 | Vercel엔 최적이지만 AWS Lambda엔 별도 어댑터 필요 | Express → `serverless-http`로 Lambda 핸들러화가 정형화되어 있음 |
| 확장성 | 백엔드 로직 커지면 나중에 분리 필요해질 수 있음 | 처음부터 관심사 분리, 추후 모바일 등 다른 클라이언트 붙이기 쉬움 |
| 적합한 상황 | 빠른 MVP, 유지보수자 1인 | API 경계를 명확히 두고 싶거나 AWS Lambda 배포를 우선할 때 |

**결정: Next.js(프론트) + Node/Express(백엔드) 분리.** 처음 요청하신 "모노레포로 프/백 같이"라는 방향과 일치하고, Lambda 배포 어댑터가 Express 기준으로 훨씬 정형화되어 있어 3.2에서 정한 배포 방식과도 궁합이 좋음.

```
daily-interview-coach/        (turborepo, pnpm workspaces)
├── apps/
│   ├── web/                  Next.js 프론트엔드
│   └── api/                  Node/Express 백엔드 (serverless-http로 Lambda 래핑)
├── packages/
│   ├── shared-types/         프론트-백엔드 공유 타입 (질문/답변/스트릭 스키마)
│   └── config/                eslint/tsconfig 공통 설정
└── infra/                     AWS CDK 또는 SST (IaC)
```

### 3.4 입력 방식 — 이력서 업로드 + Notion 링크 (둘 다 지원)

| 입력 | 처리 방식 |
| --- | --- |
| 이력서 파일 (PDF/텍스트) | 업로드 → Supabase Storage 저장 → 텍스트 추출(`pdf-parse` 등) → AI 프롬프트에 삽입 |
| Notion 페이지 링크 | Notion Integration Token 발급 필요 → 해당 페이지를 연동에 공유 → Notion API로 콘텐츠 조회 → AI 프롬프트에 삽입 |

두 입력 모두 최종적으로 "텍스트 컨텍스트"로 정규화되어 동일한 질문 생성 프롬프트에 들어감.

**원본 파일 저장소 결정: S3 대신 Supabase Storage 사용 (임시가 아닌 최종 결정).** 3.6에서 DB(Supabase)를 "AWS 밖의 별도 서비스지만 무료 티어라 실질 청구 없음"이라는 이유로 이미 예외로 받아들였고, 같은 논리가 파일 저장에도 적용됨. Free 플랜 기준 Storage 1GB 제공 — 개인 1인의 이력서 파일 용도로는 충분하고 비용 발생 없음. 프로덕션 배포(Phase 4) 이후에도 그대로 사용하며, S3로의 마이그레이션은 계획하지 않음.

**결정: Notion Integration Token (Internal) 방식으로 확정.** 공개 URL 방식(비공식 HTML 파싱, 페이지 완전 공개)보다 안정적이고 공식 지원되는 방식이라 1차는 이걸로 진행. 공개 URL 방식은 채택하지 않음.

> **⚠️ 다중 사용자 확장 시 주의**: 1차에서 쓰는 Notion Integration Token은 **Internal Integration** 방식으로, 본인의 Notion 워크스페이스 하나에만 묶임 — 다른 사용자의 워크스페이스에는 접근할 수 없음. 2차 이후 다중 사용자로 확장할 때는 **Public OAuth Integration**으로 전환이 필요함: Notion 개발자 포털에 연동을 Public으로 등록 → 사용자별로 Notion OAuth 인가(승인) 플로우 → 사용자별 액세스 토큰을 DB에 저장(`sources`/`push_subscriptions`처럼 사용자별 레코드). 1차는 1인 전용이라 Internal Token으로 충분하지만, 이 전환 작업은 2차 착수 시 반드시 고려해야 함.

### 3.5 질문 재생성 전략 — 미리 채워두기(prefetch)

질문 풀(기본 40개 + AI 생성분)을 사용자가 다 소진했을 때 어떻게 할지에 대한 결정.

| 방식 | 설명 | 채택 여부 |
| --- | --- | --- |
| 재활용 | 다 쓰면 API 재호출 없이 기존 질문을 다시 섞어서 노출 | ❌ 반복으로 지루해짐 |
| 소진 시 재호출 | 마지막 질문 답변 시점에 API 호출해 새 배치 생성 | ❌ 사용자가 대기 시간을 체감함 |
| **미리 채워두기 (선택)** | 남은 미답변 질문이 임계치(예: 5개) 이하로 줄면 백그라운드에서 다음 배치를 미리 생성해 DB에 적재. 사용자는 소진 시점을 체감하지 못함 | ✅ |

**결정: 미리 채워두기.** 새 배치를 생성할 때는 이미 생성된 질문 목록 전체를 프롬프트에 포함해 "겹치지 않게" 생성하도록 지시하고, 이력서/Notion 소스가 마지막 생성 이후 변경되었으면 최신 내용을 반영해 재생성한다. 배치당 비용은 미미한 수준(질문 20~40개 생성 1회당 수 센트)이라 부담 없음.

### 3.6 데이터베이스 — Supabase

| 항목 | Supabase | DynamoDB | RDS(Postgres) |
| --- | --- | --- | --- |
| 모델링 | SQL, 관계형 — 익숙하고 쿼리 편함 | 파티션키/정렬키 설계 필요, 학습 곡선 있음 | SQL이지만 Lambda 연결 시 VPC 필요 |
| Lambda 연결 | 커넥션 풀러(Supavisor)로 서버리스 동시성 문제 해결 | 문제 자체가 없음 (HTTP 기반) | VPC 설정 + NAT/RDS Proxy 필요해 복잡도 높음 |
| 비용 | 무료 티어(500MB)로 개인 규모 충분 | 매우 저렴, 사용량 기반 | 인스턴스 상시 과금 (Aurora Serverless도 완전 0원은 아님) |
| AWS 통합 | AWS 밖의 별도 서비스 (다만 무료 티어라 실질 청구 없음) | AWS 네이티브, 단일 청구서 원칙에 부합 | AWS 네이티브 |

**결정: Supabase.** 이 프로젝트의 쿼리 패턴(사용자별 질문 목록, 답변 기록 조회, 스트릭 계산)은 SQL로 다루기 쉽고, Lambda + RDS 조합의 VPC 복잡도를 피하면서도 관계형 모델을 그대로 쓸 수 있음. 무료 티어라 비용 부담 없음. AWS 단일 청구서 원칙에서는 약간 벗어나지만 실제 청구 금액이 없어 실질적 문제는 아님.

### 3.7 접근 제어 — 이메일 기반 방문자 게이트 (DB 조회)

**원래 결정(변경됨)**: Lambda 환경변수에 고정 API 키를 저장하고 백엔드 미들웨어에서 요청 헤더 값과 비교하는 방식. 이유: 완전 무료(SSM/Secrets Manager 대비), 개인 1인 사용 규모에 충분.

**변경 이유**: 이 고정 API 키는 `apps/api`(백엔드) ↔ Next.js 서버 사이에서만 의미가 있는데, **브라우저(방문자) ↔ Next.js 서버 사이엔 애초에 아무 게이트가 없었다.** 브라우저가 API 키를 직접 다루지 않도록 서버사이드(Next.js Route Handler/Server Action)로 옮겨도, "이 웹사이트에 누가 접속해서 써도 되는가"는 여전히 미해결 — URL만 알면(또는 우연히 접속해도) 누구나 이용 가능하고, 이 앱은 유저 구분 로직이 없어 방문자의 데이터가 고정 유저 1명의 데이터에 그대로 섞여 들어간다(이력서, 답변, 피드백 등).

**결정: 이메일 기반 방문자 게이트 + DB 조회.** API 키 방식을 폐기하고 아래로 대체한다.

1. 방문자가 가드 페이지에서 이메일 입력
2. Next.js 서버가 `users` 테이블에서 해당 이메일 존재 여부 조회 (DB 조회 — 신원 확인이므로 환경변수 고정값 대조가 아니라 실제 유저 데이터 대조가 맞는 설계)
3. 일치하면 **httpOnly + Secure 쿠키** 발급 (브라우저 JS로 읽을 수 없음, 원격 공격자가 훔쳐볼 수 없음 — 일반적인 로그인 세션 쿠키와 동일한 보호 수준)
4. 이후 요청: Next.js 서버(브라우저 JS 아님)가 쿠키를 읽어 `apps/api` 호출 시 헤더에 실어 전달
5. `apps/api`는 그 값이 `users` 테이블의 이메일과 일치하는지 확인 (기존 `requireApiKey` 미들웨어를 대체)
6. 쿠키 없거나 무효하면 가드 페이지로 리다이렉트

이메일은 비밀번호보다 약한 값(원래 공개 목적)이라는 한계는 있으나, 개인 프로젝트 노출도 대비 실용적 선택으로 판단. 사용자·트래픽이 늘어나면 그때 Cognito 등 정식 인증으로 이전 (기존 방침 유지).

### 3.8 일일 리마인더 — PWA 설치 + Web Push (고정 시간)

이메일/Slack 알림이 습관 트리거로 약하다는 최초 문제의식(1. 배경)을 앱 자체 기능으로 해결.

**구성**

1. **PWA 설치**: `manifest.json` + Service Worker 등록 → 브라우저가 "홈 화면에 추가"를 제공, 앱처럼 설치 가능
2. **푸시 구독 저장**: 설치 후 `PushManager.subscribe()`로 얻은 구독 정보(엔드포인트+키)를 Supabase에 저장
3. **발송**: EventBridge Scheduler가 **고정 cron 시간**(예: 매일 09:00 KST)에 리마인더 Lambda를 트리거 → 트리거 시점에 Supabase에서 오늘의 질문을 조회해 알림 내용을 그때 구성 → `web-push` 라이브러리로 저장된 구독 앤드포인트에 발송

**발송 시간 처리 방식 — 왜 고정인가:**

| 항목 | 알림 내용 | 발송 시간 |
| --- | --- | --- |
| 결정 시점 | Lambda가 트리거될 때마다 코드가 실행되며 매번 새로 계산 → 완전히 동적 | EventBridge cron 표현식에 값으로 박혀있는 **인프라 설정** → DB 값으로 실시간 제어되지 않음 |
| 바꾸려면 | 코드/데이터만 바뀌면 자동 반영 | cron 표현식을 고쳐서 **재배포** 필요 |

사용자가 본인 1명뿐이라 시간을 앱 설정 화면에서 동적으로 바꿀 필요가 없다고 판단 — **고정 시간(EventBridge cron)으로 채택**. 나중에 시간을 바꾸고 싶으면 `infra/`의 EventBridge 스케줄 설정에서 cron 표현식만 수정하고 재배포하면 됨 (코드 수정 없이 인프라 설정 한 줄).

> 참고로 만약 나중에 사용자별로 알림 시간을 다르게 설정하고 싶어지면, EventBridge를 짧은 주기(예: 5~15분마다)로 돌리고 Lambda가 매번 "현재 시각과 일치하는 `notify_at`을 가진 사용자"만 걸러서 보내는 방식으로 바꿔야 함 — 지금은 1인 사용자라 불필요.

**iOS 제약**: iOS Safari는 16.4 이상에서 "홈 화면에 추가된 PWA"에만 푸시가 동작함 — 아이폰에서 쓰려면 먼저 홈 화면에 추가해야 알림이 옴.

#### 3.8.1 미접속 시 알림 빈도 에스컬레이션

고정 시간(예: 21:00 KST) 알림을 보냈는데도 그날 답변하지 않은 경우, 그 다음 날부터는 알림 빈도를 늘려 재참여를 유도한다.

**결정: `streaks.last_date`를 그대로 활용해 에스컬레이션 여부를 판단.** 별도 상태 컬럼이나 플래그를 추가하지 않음.

**동작 방식**:

1. EventBridge Scheduler를 하루 1회 고정 cron에서 **18:00~24:00 KST 매시간 cron**으로 변경 (같은 리마인더 Lambda 재사용, 인프라 리소스 추가 없음)
2. Lambda 트리거마다:
   - 오늘 답변 완료(`last_date == 오늘`) → 발송 없이 종료 (중복 알림 방지)
   - 오늘 미답변이고 트리거 시각이 기존 고정 시간(21:00)인 경우 → 평소대로 발송
   - 오늘 미답변이고 `last_date != 어제`(즉 어제도 미답변 — 스트릭이 끊긴 상태)인 경우 → 21:00 외의 시간에도 발송 (에스컬레이션)
   - 그 외(어제는 답변했고 오늘은 아직 21:00 전/후가 아닌 경우) → 발송 안 함
3. 답변하는 순간 `last_date`가 오늘로 갱신되므로, 다음 날은 조건이 자동으로 꺼짐 — 별도 리셋 로직 불필요

**비용/인프라 영향**: Lambda 호출이 1일 1회 → 약 7회로 증가하는 수준이라 프리티어 내에서 무시 가능한 수준.

> 3.8 본문의 "짧은 주기 + 필터링" 대안은 **다중 사용자별 알림 시간 개인화**를 위해 기각된 것이고, 이 에스컬레이션 로직은 **미접속 시 재참여 유도**가 목적이라 별개의 결정임 — 서로 충돌하지 않음.

## 4. 핵심 플로우

1. **온보딩**: 사용자가 이력서 업로드 또는 Notion 링크 입력 (또는 둘 다)
2. **질문 생성**: 백엔드가 텍스트를 정리 → AWS Bedrock 호출(Claude 모델) → 카테고리별 맞춤 질문 N개 생성 → DB 저장
3. **일일 노출**: 매일 접속 시 미답변 질문 중 하나를 우선 노출 (기존 40개 기본 질문 + AI 생성 질문 합쳐서 운용). 미답변 질문이 임계치 이하로 줄면 백그라운드에서 다음 배치를 미리 생성(3.5 참고)
4. **답변 기록**: 텍스트로 답변 작성 → 저장 → 스트릭 갱신
5. **AI 피드백 (온디맨드)**: 답변 저장 후 사용자가 "AI 피드백 받기"를 누르면, 질문+답변을 AWS Bedrock(Claude 모델)에 보내 강점/개선점/예상 후속 질문 형태의 피드백을 받아 답변에 첨부. 자동 호출이 아닌 사용자가 원할 때만 호출 — 빠른 기록 흐름을 방해하지 않기 위함
6. **회고**: 기록 목록에서 과거 질문/답변(+AI 피드백) 조회, 마크다운 내보내기
7. **일일 리마인더**: PWA로 설치해두면 매일 고정 시간(EventBridge cron)에 오늘의 질문 알림이 푸시로 도착 → 탭하면 오늘의 질문 화면으로 이동 (3.8 참고)

| --- | --- | --- |
| Phase 0 | 레포 생성, 모노레포 스캐폴딩 (turborepo/pnpm) | 빈 apps/web, apps/api 실행 확인 |

| Phase 4 | AWS 인프라 구성 (Lambda+API Gateway, S3) + Supabase 프로덕션 연결 + EventBridge Scheduler(고정 cron) 리마인더 발송 Lambda + 배포 | 실제 URL로 접속 가능, 고정 시간에 푸시 도착 확인 |
| Phase 5 | 도메인 연결, 모니터링(CloudWatch), 비용 알람 | 운영 준비 완료 |

**실행 순서 변경 (2026-08-07)**: 위 표는 Phase별 최종 산출물 기준이며, 실제 착수 순서는 Phase 2를 전부 끝낸 뒤 Phase 3을 시작하지 않는다. 대신 **기능 단위로 백엔드+프론트를 함께(vertical slice) 진행** — 예: "이력서 업로드"는 API(Phase 2)와 화면(Phase 3)을 같은 기능 단위로 묶어 처리. 이유: curl로만 검증하며 백엔드를 전부 쌓기보다, 실제 화면에서 눈으로 확인하며 가는 게 개인 프로젝트 진행에 더 낫다고 판단. "AI 답변 피드백"은 답변이 쌓인 후에야 의미가 있어 예외적으로 가장 마지막으로 유지. 착수 순서와 현재 상태는 [`progress.md`](./progress.md)에서 실시간으로 관리.

## 7. 열린 질문 / 리스크

- **이력서 파싱 정확도**: PDF 레이아웃에 따라 텍스트 추출 품질 편차 가능 — 1차는 단순 텍스트 추출로 시작, 필요시 개선.
- **비용**: Bedrock 호출량 + Lambda/S3 비용은 개인 사용 규모에서는 미미할 것으로 예상되나, AWS 요금 알람(Budget Alert) 설정 권장. Supabase는 무료 티어 내 사용 유지.
- **Bedrock 모델 액세스**: `ap-northeast-2`에서 Claude 모델 액세스를 콘솔에서 신청해야 함 — 진행 전 확인 필요.
- **iOS 푸시 제약**: iOS 16.4 이상에서만, 홈 화면에 추가된 PWA에 한해 웹 푸시가 동작함(3.8). 아이폰 사용 시 최초 설치 안내 필요.

> 현재 진행 상황(완료/다음 액션)은 [`progress.md`](./progress.md)에서 관리합니다.
