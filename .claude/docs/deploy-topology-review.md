## 발단

`client-data-strategy.md` 31번 줄의 _"RSC의 진짜 강점(DB/ORM을 서버 컴포넌트에서 네트워크 홉 없이 직접 접근)"_ 이 무슨 의미인지 확인하는 데서 시작해, "그 강점이 이 앱에서 왜 안 나오는가" → "그럼 배포는 어떻게 해야 하는가" → "클라이언트 데이터 전략은 최선이었나"로 확장됨.

## 1. 확인된 사실

### 1.1 `apps/web` 배포 방식은 PRD에서 정해진 적이 없다

Phase 4의 `(Lambda+API Gateway, S3)`와 7절 `Lambda/S3 비용`에 나오는 **S3는 웹 호스팅이 아니라 이력서 파일 저장소**였다. 최초 커밋(`2d0b9c5`)의 3.5절이 _"이력서 파일 → S3 저장"_ 이었고, 이후 3.5가 **Supabase Storage로 최종 변경**되었는데 Phase 4와 7절은 함께 고쳐지지 않아 잔재로 남았다.

→ **PRD 잔재 2줄 정정 필요** (미실행)

### 1.2 S3 정적 호스팅은 애초에 이 앱과 양립 불가

서버 실행에 의존하는 지점:

```
middleware.ts:22          미인증 요청을 HTML이 나가기 전에 게이트로 리다이렉트
app/gate/page.tsx:18,22   서버에서 쿠키 확인 → 통과했으면 즉시 원래 경로로
app/today/page.tsx:17     서버 렌더 중 401 감지 → redirect()
lib/apiClient.ts:1-2      server-only + next/headers로 쿠키 전달
```

쿠키 기반 유저별 인증으로 라우트가 dynamic으로 전환되므로 정적 export 대상이 아니다.

### 1.3 Next를 쓰는 실제 근거는 RSC의 DB 직접 접근이 아니다

분리된 Express API 구조라 RSC든 클라이언트 fetch든 `apps/api`로 HTTP 홉을 낸다. RSC가 절약해 주는 홉이 이 구조에는 없다. (이 사실은 4절 클라이언트 데이터 전략 재검토의 출발점이기도 하다.)

실제 근거는 **서버 사이드 인증 게이트** — 미인증 상태가 브라우저에 한 프레임도 노출되지 않는다. SPA에서는 빈 셸을 먼저 그리고 JS 로드 후 인증을 확인하므로 로딩 플래시가 발생한다.

> RSC를 Next 없이 쓰는 것은 실익 없음. RSC는 React 기능이지만 RSC를 아는 번들러 + flight 스트림 서버 런타임 + 모듈 그래프 분리 + 라우팅이 필요하고, 그 묶음의 성숙한 구현이 Next App Router다. **RSC를 원하면 Next가 답이고, Next를 뺀다면 RSC도 같이 버리는 게 일관됨.**

## 2. 검토한 선택지

**중간은 없다.** Next를 쓰면서 정적 배포하려는 시도가 그 중간이고 성립하지 않는다.

## 3. 배포 토폴로지: EC2 코로케이션 (확정)

`apps/web` + `apps/api`를 같은 EC2 한 대에 올린다.

```
현재 PRD 계획:  Next 서버 → [API GW] → [Lambda 콜드스타트] → Supavisor → Postgres
확정:           Next 서버 → localhost:3001 (Express) → Supavisor → Postgres
                            └ 루프백, sub-ms ┘
```

### 근거

1. **콜드스타트 없음, 그리고 회피 수단이 없음.** 사용자 1명이 하루 한 번 쓰는 패턴이면 Lambda는 사실상 매 요청이 콜드. 통상 범위는 Node + 무거운 번들(Express + AWS SDK v3 + `pdf-parse`) 500ms~1.5s, OpenNext로 올린 Next 서버는 1s 이상 흔함 — **이 앱의 측정값은 아니며 실측 필요.** Lambda SnapStart는 Node.js를 지원하지 않아(Java/Python/.NET만) 이 런타임엔 무료로 콜드스타트를 없앨 방법이 없다 — 확인된 사실.
2. **장기적으로 컨테이너 + ECS/EKS 지향.** `EC2 → Docker → ECS → EKS`는 각 단계가 앞 단계 위에 쌓이는 사다리. 서버리스 Next(C)는 그 경로와 무관한 패러다임이라 발판이 하나도 안 쌓인다. **이게 C를 접은 결정적 이유.**
3. **CORS/`SameSite` 문제 원천 소멸.** nginx로 `/api`를 웹과 같은 도메인에 붙이면 프로덕션이 동일 오리진이 된다.
4. **외부 노출 원천 차단.** Express를 `127.0.0.1:3001`에 바인딩하면 루프백에만 붙으므로 외부에서 접근 경로가 없다. 보안그룹은 443(+SSH)만 열면 됨.

### 지켜낼 것

-   `apps/api`는 모노레포 안에서 독립 Express 앱으로 유지 — 이유·트레이드오프는 4절 "Express를 독립 HTTP 서비스로 유지할지" 참고
-   **바뀌는 것은 배포 토폴로지뿐, 코드 구조는 그대로**
-   리마인더는 EventBridge + Lambda 유지 (EC2가 죽어도 알림 경로 생존)

### 감수할 것

-   프리티어 이탈(상시 과금), 단일 인스턴스 SPOF, 패치·프로세스 관리·TLS 직접 담당
-   → **Budget Alert를 Phase 4 착수 전에** 걸어둔다 (PRD는 Phase 5에 배치)
-   ALB는 인스턴스보다 비쌀 수 있음 → nginx + Elastic IP + certbot 또는 CloudFront → EC2

### API Gateway + Lambda 학습은 프로덕션을 걸지 않고

`serverless-http` 래핑이 이미 있으므로, CDK로 HTTP API + Lambda를 한 번 올려 **event 형태를 직접 확인 + 콜드스타트 실측 → `remove`로 정리**. 상시 비용 없고 순서에 묶이지 않는 별도 트랙. 실측값은 면접 서사에도 그대로 쓰인다.

## 4. 클라이언트 데이터 전략 + Express 독립 유지 (확정)

### 클라이언트 데이터 전략: 서버 우선 (RSC 읽기 + Server Actions)

**결정**: 클라이언트 데이터 접근을 서버 우선(RSC 읽기 + Server Actions)으로 통일한다. TanStack Query는 도입하지 않는다.

**근거**

1. **서버 읽기가 더 빠름.** EC2 코로케이션에서 RSC 읽기는 `Next 서버 → localhost`(sub-ms)로 끝나지만, 클라이언트 `useQuery`는 `브라우저 → 인터넷 → Express`(사용자 회선, 수십~100ms)를 거쳐야 한다.
2. **다중 작성자/소비자 상황이 아님.** 사용자 1명이면 작성자도 1명이라 데이터가 남의 행동으로 낡아지지 않는다. TanStack Query의 핵심 가치(백그라운드 refetch, stale-while-revalidate, 컴포넌트 간 캐시 공유, 멀티탭 동기화, 폴링)는 다중 작성자/다중 소비자 상황을 겨냥하는데, 이 앱엔 해당하지 않는다.
3. **왕복 횟수가 더 적음.** 답변 제출 후 다음 질문으로 넘어가는 흐름 기준:

    ```
    TanStack Query:  ① 브라우저 →[인터넷]→ Express → Supabase   (답변 저장)
                     ② 브라우저 →[인터넷]→ Express → Supabase   (invalidate → refetch)
                     → 사용자 회선 왕복 2회 (직렬)

    Server Actions:  ① 브라우저 →[인터넷]→ Next 서버
                          ├ loopback → Express → Supabase        (저장)
                          └ loopback → Express → Supabase        (재조회, 병렬 가능)
                     ② 재렌더된 RSC 페이로드를 같은 응답에 실어 반환
                     → 사용자 회선 왕복 1회
    ```

4. **새 의존성이 없음.** provider/hydration 세팅, 서버·클라이언트 겸용(isomorphic) queryFn, 별도의 401 게이트 처리 구현이 필요 없다 — 기존 `apiClient.ts`를 그대로 쓴다.
5. **PWA 오프라인 읽기가 요구사항이 아님.** PRD 3.8 확인 결과 PWA 도입 목적은 웹 푸시뿐(iOS Safari가 "홈 화면에 추가된 PWA"에만 푸시를 허용하기 때문)이고, 오프라인 읽기는 요구사항으로 없다.

**감수하는 트레이드오프**: Server Actions의 에러 처리는 `useMutation`보다 투박함(세밀한 `errorSource` 분기는 손으로 처리), 순차 POST라 병렬 변이 불가, `revalidatePath`는 라우트 전체를 무효화함. TanStack Query의 낙관적 업데이트만큼 체감 속도를 내려면 별도 구현이 필요함. `ResumeUploadForm`의 `useState` 7개는 어느 쪽을 택해도 크게 줄지 않음(파일 선택+업로드+생성 트리거+에러 출처 구분이 그 UX에 내재).

**파생 결론**: 브라우저는 Express를 직접 호출하지 않는다. `ResumeUploadForm`/`GateForm`의 인라인 `fetch(NEXT_PUBLIC_...)` 코드는 Server Action으로 전환한다 — Express를 `127.0.0.1`에 바인딩하면 외부 접근 자체가 막히므로 이건 선호가 아니라 필수 변경이다.

#### 채택하지 않은 대안

| 대안                                    | 채택하지 않은 이유                                                                                                                                                                                                                                       |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TanStack Query 단일화 (클라이언트 캐시+무효화) | 위 근거 1~5. 특히 provider/hydration/isomorphic queryFn 같은 새 의존성이 필요하고, 이 앱엔 다중 작성자/소비자 상황이 없어 캐시+무효화가 처리할 일감 자체가 얇음                                                                                          |
| `unstable_cache` 유저별 서버 캐싱          | 캐시 함수 안에서 `cookies()`/`headers()` 사용 불가(키 결정성 제약)라 현재 쿠키 기반 인증(`apiClient`)을 그대로 못 감쌈. 단일 사용자 + 자주 바뀌는 데이터라 캐시 히트 윈도가 짧고 loopback이 이미 저렴해 payoff 얇음. `unstable_` API 불안정(Next 15 `'use cache'`로 재편 중) + 크로스 유저 유출 footgun |

### Express를 독립 HTTP 서비스로 유지할지 (확정: 유지)

위 결론대로 Next↔Express가 항상 `localhost:3001` 루프백을 거치는 구조가 되면서, "차라리 Next가 DB에 직접 접근하고 Express를 없애면 더 빠르지 않나"라는 질문이 자연히 따라옴. `infra-concepts.md` 1절 지연 계단 기준으로 보면 맞는 말이다 — 모놀리식 Next+DB 직접 접근은 1번 칸(같은 프로세스, 직렬화 없음), Next→Express 루프백은 2번 칸(수십 µs~1ms, 직렬화 있음)이라 병합 쪽이 이론상 더 빠르다.

**결론: 그래도 Express는 독립 HTTP 서비스로 유지한다.** 이유는 속도가 아니라 아래 "얻는 것" 항목들이고, 잃는 것은 대부분 이 앱 규모에서 체감 불가능하거나 이미 다른 이유로 지불 중인 비용이다.

| 타입 계약 수동 동기화  | API 모양이 바뀔 때마다 Express 라우트·`shared-types`·Next 소비 코드 세 곳을 손으로 맞춤                    | **zod 스키마 + `z.infer`** 로 런타임 검증과 타입을 하나의 정의에서 생성 (OpenAPI+`openapi-typescript`는 비-TS 클라이언트가 실제로 생기기 전까진 스펙을 손으로 유지해야 해 동기화 지점이 오히려 하나 더 늘어남) | 아직 미도입 — 이 논의와 별개로 apps/api에 요청 검증 로직 자체가 없다는 공백도 같이 메우는 작업이라 가치는 있으나, 우선순위상 후순위로 미룸                                                                                           |
| 미사용 유연성에 선지불 | 모바일 클라이언트·대량 트래픽 재분리 등 지금 스코프에 없는 미래를 위해 매일 구조적 비용(위 4항목)을 지불   | 지금은 병합, 필요해지는 시점에 한 번만 분리 비용 지불(YAGNI)                                                                                                                                                    | 이 프로젝트는 "면접 서사·컨테이너 학습 사다리"가 실용적 필요와 별개의 정당화 축으로 작동함(3절 EC2 결정과 같은 논리) — API Gateway 학습 트랙 자체가 이미 이 유연성의 실사용처라, 순수 낭비로 보기 어려움                            |

## 5. 미실행 후속 작업

1. **배포 토폴로지/클라이언트 전략 확정을 문서에 반영** → 이 문서를 결정 문서로 승격 또는 `deploy-topology.md` 신규 작성
2. **PRD 잔재 2줄 정정** — Phase 4의 `S3`, 7절 `Lambda/S3 비용`. 3.2를 폐기 표기할지 "5.x에서 대체됨" 참조만 남길지 미정
3. **`progress.md` 갱신** — 아래 제안

### `progress.md` 다음 액션 제안 순서

```
1. ~~이력서 업로드 UI~~ — 완료
2. AI 질문 생성 API — spec/test 완료, developer 단계부터 재개
3. 클라이언트 데이터 계층을 서버 우선(RSC+Server Actions)으로 전환 — 4번보다 먼저 (답변 피드백 UI를 처음부터 단일 패러다임으로)
4. AI 답변 피드백 API + UI
5. Phase 4 배포 — EC2 코로케이션, nginx로 /api를 같은 도메인에
6. Notion 연동 — 2차로 미룸 (기존 이유 유지)

별도 트랙 (순서 무관): API Gateway + Lambda 실습 → event 형태 확인 + 콜드스타트 실측 → remove
```

**판단이 들어간 지점 두 개**

-   **클라이언트 데이터 계층 전환을 답변 피드백보다 앞에** — 뒤로 미루면 답변 피드백 UI를 인라인 `fetch`로 짜고 다시 고치게 된다. 단 질문 생성(2번)은 이미 spec/test가 현재 방식 기준으로 나와 있으니 그대로 끝낸다(지금 패러다임을 바꾸면 작성된 테스트가 무효).
-   **배포를 5번으로 뒤에** — 상시 과금 EC2를 일찍 켜면 개발 기간 내내 비용을 낸다. 일찍 배포해 얻는 "실제 환경 검증" 이점은 코로케이션이라 상당 부분 사라진다(동일 오리진이므로 CORS/`SameSite` 문제가 발생하지 않고, 로컬 `:3000` ↔ `:3001`과 사실상 같은 조건). 반면 API Gateway 실습은 올렸다 지우면 되니 순서에 묶지 않는다.

## 6. 면접용 서사 (이력서 기록 시)

**"성능 때문에 합쳤다"고 말하면 안 된다.** 사실이 아니고("체감 지연을 지배하는 건 홉이 아니라 Bedrock 호출"), 측정값 없이 말하면 후속 질문에서 무너진다.

정직하고 더 강한 서사:

> 서버리스(Lambda+API Gateway)로 설계했으나, RSC의 쿠키 기반 인증이 라우트를 dynamic으로 만들어 정적 배포가 불가능해지고 상시 서버가 필요해진 시점에 배포 토폴로지를 EC2 단일 인스턴스 코로케이션으로 재결정했다. 앱 경계와 `serverless-http` 래핑은 유지해 되돌릴 수 있게 설계했다.

**"왜 Next인가"에 "RSC로 DB를 직접 접근할 수 있어서"라고 답하면 안 된다** — 분리된 API 구조에서 그 이점은 나오지 않는다(1.3절). 실제 이유는 서버 사이드 인증 게이트이고, 그 대가로 정적 배포를 포기했다고 말해야 한다. 프레임워크의 대표 세일즈 포인트가 자기 구조에서는 작동하지 않는다는 걸 아는 게 그 포인트를 읊는 것보다 좋은 신호다.

### 예상 후속 질문

| 질문                                     | 답변 방향                                                                                                                                                                       |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 왜 Next 풀스택 + DB 직접 접근이 아닌가   | 검토함(4절 "Express를 독립 HTTP 서비스로 유지할지"). EventBridge 리마인더가 Next와 무관하게 DB를 읽어야 해 백엔드 로직이 완전히 사라지지 않고, API 경계는 다른 클라이언트 여지로 남김. 루프백 홉 비용은 Bedrock 호출에 묻혀 체감 안 됨 |
| ECS/EKS는 왜 안 썼나                     | 이 규모에 k8s가 푸는 문제가 없음. EKS는 워크로드와 무관한 컨트롤 플레인 고정비. 앱을 먼저 돌린 뒤 컨테이너화 → ECS → EKS 순서로 의도적 학습 단계로 계획                          |
| 실제 트래픽이 생기면                     | 코로케이션의 근거 자체가 사라짐. `serverless-http`를 남긴 이유가 그것, 또는 ALB 뒤 ECS. **결정이 스케일 의존적임을 알고 내렸다**는 게 포인트                                    |
| 단일 EC2 SPOF 아닌가                     | 맞고 수용. 단 알림 경로는 EventBridge+Lambda라 박스와 독립                                                                                                                       |
| EC2인데 DB를 왜 RDS가 아니라 Supabase로  | **찔릴 수 있는 지점.** RDS를 뺀 근거 중 하나가 "Lambda 연결 시 VPC 필요"였고 EC2면 그 부담이 줄어 근거가 약해짐. 정직한 답: 무료 티어 + 이미 스키마·Storage까지 올라가 있어 옮길 이득이 없었음  |
