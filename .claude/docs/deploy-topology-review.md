## 1. 확인된 사실

### 1.1 `apps/web` 배포 방식은 PRD에서 정해진 적이 없다

Phase 4의 `(Lambda+API Gateway, S3)`와 7절 `Lambda/S3 비용`에 나오는 **S3는 웹 호스팅이 아니라 이력서 파일 저장소**였다. 최초 커밋(`2d0b9c5`)의 3.5절이 *"이력서 파일 → S3 저장"* 이었고, 이후 3.5가 **Supabase Storage로 최종 변경**되었는데 Phase 4와 7절은 함께 고쳐지지 않아 잔재로 남았다.

→ **PRD 잔재 2줄 정정 필요** (미실행)

### 1.2 S3 정적 호스팅은 애초에 이 앱과 양립 불가

서버 실행에 의존하는 지점:

```
middleware.ts:22          미인증 요청을 HTML이 나가기 전에 게이트로 리다이렉트
app/gate/page.tsx:18,22   서버에서 쿠키 확인 → 통과했으면 즉시 원래 경로로
app/today/page.tsx:17     서버 렌더 중 401 감지 → redirect()
lib/apiClient.ts:1-2      server-only + next/headers로 쿠키 전달
```

쿠키 기반 유저별 인증으로 라우트가 dynamic으로 전환되므로 정적 export 대상이 아니다.

### 1.3 Next를 쓰는 실제 근거는 RSC의 DB 직접 접근이 아니다

분리된 Express API 구조라 RSC든 클라이언트 fetch든 `apps/api`로 HTTP 홉을 낸다. RSC가 절약해 주는 홉이 이 구조에는 없다.

실제 근거는 **서버 사이드 인증 게이트** — 미인증 상태가 브라우저에 한 프레임도 노출되지 않는다. SPA에서는 빈 셸을 먼저 그리고 JS 로드 후 인증을 확인하므로 로딩 플래시가 발생한다.

> RSC를 Next 없이 쓰는 것은 실익 없음. RSC는 React 기능이지만 RSC를 아는 번들러 + flight 스트림 서버 런타임 + 모듈 그래프 분리 + 라우팅이 필요하고, 그 묶음의 성숙한 구현이 Next App Router다. **RSC를 원하면 Next가 답이고, Next를 뺀다면 RSC도 같이 버리는 게 일관됨.**

## 2. 검토한 선택지

| | A. EC2 코로케이션 | B. Vite SPA + S3/CloudFront + Lambda | C. 서버리스 Next (OpenNext/SST) |
| --- | --- | --- | --- |
| 인증 게이트 | 서버에서, 플래시 없음 | 클라이언트에서, 플래시 있음 | 서버에서, 플래시 없음 |
| 데이터 계층 | 선택 자유 | TanStack Query 단일, 가장 단순 | prefetch + hydration 필요 |
| 비용 | 상시 과금 | 프리티어 내 | 프리티어 내 |
| 서버 운영 | 직접 담당 | 없음 | 없음 |
| 콜드스타트 | **없음** | 있음 (API만) | 있음 (**웹까지**) |
| 컨테이너/k8s 학습 발판 | 웹+API 둘 다 | API만 | **없음 — 다른 패러다임** |
| RSC 경험 | 있음 | 없음 | 있음 |

**중간은 없다.** Next를 쓰면서 정적 배포하려는 시도가 그 중간이고 성립하지 않는다.

## 3. 현재 기울기 (미확정) — A. EC2 코로케이션

`apps/web` + `apps/api`를 같은 EC2 한 대에 올린다.

```
현재 PRD 계획:  Next 서버 → [API GW] → [Lambda 콜드스타트] → Supavisor → Postgres
A:              Next 서버 → localhost:3001 (Express) → Supavisor → Postgres
                            └ 루프백, sub-ms ┘
```

### 근거

1. **콜드스타트 없음.** 사용자 1명이 하루 한 번 쓰는 패턴이면 Lambda는 사실상 매 요청이 콜드. 통상 범위는 Node + 무거운 번들(Express + AWS SDK v3 + `pdf-parse`) 500ms~1.5s, OpenNext로 올린 Next 서버는 1s 이상 흔함 — **이 앱의 측정값은 아니며 실측 필요.**
2. **장기적으로 컨테이너 + ECS/EKS 지향.** `EC2 → Docker → ECS → EKS`는 각 단계가 앞 단계 위에 쌓이는 사다리. 서버리스 Next(C)는 그 경로와 무관한 패러다임이라 발판이 하나도 안 쌓인다. **이게 C를 접은 결정적 이유.**
3. **CORS/`SameSite` 문제 원천 소멸.** nginx로 `/api`를 웹과 같은 도메인에 붙이면 프로덕션이 동일 오리진이 된다.
4. **외부 노출 원천 차단.** Express를 `127.0.0.1:3001`에 바인딩하면 루프백에만 붙으므로 외부에서 접근 경로가 없다. 보안그룹은 443(+SSH)만 열면 됨.

### 지켜낼 것

-   `apps/api`는 모노레포 안에서 독립 Express 앱으로 유지, `packages/shared-types` 유지
-   `serverless-http` 래핑 제거하지 않음 → 되돌릴 여지 + 학습 실습에 재사용
-   **바뀌는 것은 배포 토폴로지뿐, 코드 구조는 그대로**
-   리마인더는 EventBridge + Lambda 유지 (EC2가 죽어도 알림 경로 생존)

### 감수할 것

-   프리티어 이탈(상시 과금), 단일 인스턴스 SPOF, 패치·프로세스 관리·TLS 직접 담당
-   → **Budget Alert를 Phase 4 착수 전에** 걸어둔다 (PRD는 Phase 5에 배치)
-   ALB는 인스턴스보다 비쌀 수 있음 → nginx + Elastic IP + certbot 또는 CloudFront → EC2

### API Gateway + Lambda 학습은 프로덕션을 걸지 않고

`serverless-http` 래핑이 이미 있으므로, CDK로 HTTP API + Lambda를 한 번 올려 **event 형태를 직접 확인 + 콜드스타트 실측 → `remove`로 정리**. 상시 비용 없고 순서에 묶이지 않는 별도 트랙. 실측값은 면접 서사에도 그대로 쓰인다.

## 4. `client-data-strategy.md` 재검토 (미결)

TanStack Query는 **아직 미설치** → 되돌리는 비용 0.

### 문제 제기 자체는 유효

`ResumeUploadForm.tsx`에 데이터 페칭 부기용 `useState` 7개, `EmptyQuestionState.tsx`에 3개. 표준화가 필요하다는 진단은 맞다.

### 흔들린 근거

**근거 1 (분리된 API라 RSC 강점 없음)** — 결론의 방향이 역전된다. 문서는 *"RSC든 useQuery든 어차피 HTTP 홉"* 이라며 무승부로 봤지만, 코로케이션 후에는:

```
RSC 읽기:  Next 서버 → localhost (sub-ms)
useQuery:  브라우저 → 인터넷 → apps/api (사용자 회선, 수십~100ms)
```

무승부가 아니라 **서버 읽기 우위**. 이 근거는 이제 반대쪽을 지지한다.

**근거 2 (데이터가 계속 바뀌니 캐시+무효화가 할 일이 있다)** — 가장 약하다. **사용자 1명이면 작성자도 1명.** 데이터가 남의 행동으로 낡아지지 않고, 모든 변화가 같은 탭에서 내가 누른 결과다. TanStack Query의 핵심 가치(백그라운드 refetch, stale-while-revalidate, 컴포넌트 간 캐시 공유, 멀티탭 동기화, 폴링)는 대부분 **다중 작성자/다중 소비자** 상황을 겨냥한다.

**Server Actions 배제 근거도 약해진다.** 문서 41~42번 줄의 *"dynamic이라 revalidate가 매 요청 풀 서버 재렌더로 쪼그라든다"* 는 사실이지만, 코로케이션에서 그 재렌더는 **Supabase 왕복 한 번**이다. 게다가 Server Action 후 Next는 재렌더된 RSC 페이로드를 **같은 응답에 실어 보내므로** 페이지 새로고침도 별도 왕복도 없다.

### 왕복 비교 — 답변 제출 후 질문이 넘어가는 흐름

```
TanStack Query:  ① 브라우저 →[인터넷]→ Express → Supabase   (답변 저장)
                 ② 브라우저 →[인터넷]→ Express → Supabase   (invalidate → refetch)
                 → 사용자 회선 왕복 2회 (직렬)

Server Actions:  ① 브라우저 →[인터넷]→ Next 서버
                      ├ loopback → Express → Supabase        (저장)
                      └ loopback → Express → Supabase        (재조회, 병렬 가능)
                 ② 재렌더된 RSC 페이로드를 같은 응답에 실어 반환
                 → 사용자 회선 왕복 1회
```

단, **TanStack Query는 낙관적 업데이트로 체감이 더 빠를 수 있다** — 실제 지연과 체감 지연이 갈리는 지점.

### 덜 평가된 대안: 서버 우선 단일화

문서는 선택지를 *"3개 패턴 공존 vs TanStack Query 단일화"* 로 놓았으나, **RSC 읽기 + Server Actions 변이**도 단일 패러다임이다. 문서는 Server Actions를 기존 읽기 구조에 덧붙이는 변이 수단으로 평가했고, **경쟁하는 표준화 축으로는 평가하지 않았다.**

| | TanStack Query 단일화 | 서버 우선 단일화 |
| --- | --- | --- |
| 새 의존성 | 있음 (+ provider, hydration 규약) | **없음** |
| isomorphic queryFn | **필요** — 문서 56번 줄이 지목한 최대 리스크 | 불필요 |
| 401 → 게이트 규약 | `apiClient` 외에 한 번 더 구현 | `apiClient.ts` 그대로 |

56번 줄이 스스로 경고한 *"대충 하면 이중 페칭이나 prefetch 경로 인증 누락"* 조각은 **오직 TanStack Query 선택을 위해서만 존재**하고, 서버 우선에는 대응물이 없다.

**공정하게 — 서버 우선도 만능은 아니다**: Server Actions의 에러 처리는 `useMutation`보다 투박하고(세밀한 `errorSource` 분기는 손으로), 순차 POST라 병렬 변이가 안 되고, `revalidatePath`는 라우트 전체를 무효화한다. 그리고 **`ResumeUploadForm`의 `useState` 7개는 어느 쪽을 골라도 크게 줄지 않는다** — 파일 선택 + 업로드 + 이어지는 생성 트리거 + 에러 출처 구분은 상당 부분 그 UX에 내재된 상태다.

### 문서가 놓친, TanStack Query에 유리한 근거

**PWA 오프라인 읽기.** 클라이언트 캐시는 네트워크 없이도 마지막으로 읽은 데이터를 보여줄 수 있고, 서버 렌더링은 원리적으로 불가능하다(서버에 못 닿으면 받을 HTML이 없음). 문서는 이걸 한 번도 언급하지 않았다.

단, **PRD 3.8의 PWA 목적은 웹 푸시**다 — iOS Safari가 "홈 화면에 추가된 PWA"에만 푸시를 허용하기 때문. 오프라인 읽기는 PRD 어디에도 요구사항으로 없다.

### 결정 요인

**PWA 오프라인 읽기가 요구사항인가?**

-   **예** → TanStack Query. 서버 우선으로는 불가능하고, 문서의 결정이 (문서가 적지 않은 이유로) 옳았던 셈
-   **아니오** → 서버 우선이 더 단순. **현재 문서상의 답은 "아니오"**

어느 쪽이든 문서 14번 줄 **"혼용 금지"** 원칙은 그대로 유지한다.

**판단이 들어간 지점 두 개**

-   **TanStack Query를 답변 피드백보다 앞에** — 뒤로 미루면 답변 피드백 UI를 인라인 `fetch`로 짜고 다시 고치게 된다. 단 질문 생성(2번)은 이미 spec/test가 현재 방식 기준으로 나와 있으니 그대로 끝낸다(지금 패러다임을 바꾸면 작성된 테스트가 무효).
-   **배포를 5번으로 뒤에** — 상시 과금 EC2를 일찍 켜면 개발 기간 내내 비용을 낸다. 일찍 배포해 얻는 "실제 환경 검증" 이점은 코로케이션이라 상당 부분 사라진다(동일 오리진이므로 CORS/`SameSite` 문제가 발생하지 않고, 로컬 `:3000` ↔ `:3001`과 사실상 같은 조건). 반면 API Gateway 실습은 올렸다 지우면 되니 순서에 묶지 않는다.

## 6. 면접용 서사 (이력서 기록 시)

**"성능 때문에 합쳤다"고 말하면 안 된다.** 사실이 아니고("체감 지연을 지배하는 건 홉이 아니라 Bedrock 호출"), 측정값 없이 말하면 후속 질문에서 무너진다.

정직하고 더 강한 서사:

> 서버리스(Lambda+API Gateway)로 설계했으나, RSC의 쿠키 기반 인증이 라우트를 dynamic으로 만들어 정적 배포가 불가능해지고 상시 서버가 필요해진 시점에 배포 토폴로지를 EC2 단일 인스턴스 코로케이션으로 재결정했다. 앱 경계와 `serverless-http` 래핑은 유지해 되돌릴 수 있게 설계했다.

**"왜 Next인가"에 "RSC로 DB를 직접 접근할 수 있어서"라고 답하면 안 된다** — 분리된 API 구조에서 그 이점은 나오지 않는다. 실제 이유는 서버 사이드 인증 게이트이고, 그 대가로 정적 배포를 포기했다고 말해야 한다. 프레임워크의 대표 세일즈 포인트가 자기 구조에서는 작동하지 않는다는 걸 아는 게 그 포인트를 읊는 것보다 좋은 신호다.

### 예상 후속 질문

| 질문 | 답변 방향 |
| --- | --- |
| 왜 Next 풀스택 + DB 직접 접근이 아닌가 | 검토함. EventBridge 리마인더가 Next와 무관하게 DB를 읽어야 해 백엔드 로직이 완전히 사라지지 않고, API 경계는 다른 클라이언트 여지로 남김. 코로케이션이 이미 홉을 없애 재작성 대비 이득이 얇았음 |
| ECS/EKS는 왜 안 썼나 | 이 규모에 k8s가 푸는 문제가 없음. EKS는 워크로드와 무관한 컨트롤 플레인 고정비. 앱을 먼저 돌린 뒤 컨테이너화 → ECS → EKS 순서로 의도적 학습 단계로 계획 |
| 실제 트래픽이 생기면 | 코로케이션의 근거 자체가 사라짐. `serverless-http`를 남긴 이유가 그것, 또는 ALB 뒤 ECS. **결정이 스케일 의존적임을 알고 내렸다**는 게 포인트 |
| 단일 EC2 SPOF 아닌가 | 맞고 수용. 단 알림 경로는 EventBridge+Lambda라 박스와 독립 |
| EC2인데 DB를 왜 RDS가 아니라 Supabase로 | **찔릴 수 있는 지점.** RDS를 뺀 근거 중 하나가 "Lambda 연결 시 VPC 필요"였고 EC2면 그 부담이 줄어 근거가 약해짐. 정직한 답: 무료 티어 + 이미 스키마·Storage까지 올라가 있어 옮길 이득이 없었음 |
